1. [FAIT 2026-08-06] Checkpoint (dev dependency) - PR #192 (commit d03d9bd)
   - Scanner de securite Laravel : 26 checks (CVE dependances, injection, CSRF,
     mass-assignment, cookies/session non securises, CORS, TLS desactive, debug en prod...)
   - Installe en dev-only, config publiee dans config/checkpoint.php
   - Au passage : les 2 vulnerabilites Dependabot signalees (guzzlehttp/guzzle CVE-2026-69246
     + CVE-2026-69245) etaient corrigees par une simple mise a jour 7.15.1 -> 7.15.3
     -> `composer audit` clean
   - Scan de reference (apres whitelist des faux positifs) : 23 passed, 3 warning(s), 0 failed
     Warnings restants (non bloquants, pas des faux positifs) :
       - Environment Configuration : normal en local (APP_DEBUG/APP_ENV/SESSION_SECURE_COOKIE),
         deja suivi comme point "important avant lancement" ailleurs
       - File Permissions (.env 644) : lie au filesystem WSL/Windows monte, pas actionnable ici
       - Supply Chain Tooling : suggestion d'installer Aikido Safe-Chain (npm), facultatif, pas fait
   - Commande : `php artisan checkpoint:scan` (ne tourne pas sous PHP Windows natif, manque
     pcntl/posix -> executer depuis WSL Ubuntu)
   - Limite : pattern-matching statique, pas une preuve d'exploitabilite -> lire les resultats, pas confiance aveugle

3. [FAIT 2026-08-06] spatie/laravel-webhook-client
   - Verifie d'abord que le webhook Stripe maison avait 2 vrais trous : aucun
     logging/tracabilite des events recus (juste un Log::warning isole), pas de dedup
     par event.id Stripe, et traitement 100% synchrone dans la requete HTTP (pas de
     retry local sur erreur transitoire) - cf. entree ci-dessous, deplacee de "A VERIFIER"
   - Integration en "couche fine" plutot que la route/config du package : la route/le
     controller par defaut du package (`Route::webhooks()`) auraient remplace
     StripeWebhookController et change les codes de reponse (400 -> 500 par defaut sur
     signature invalide, InvalidWebhookSignature n'a pas de render()) - pas acceptable
     sur l'unique point de confirmation des paiements. Seuls le modele `WebhookCall`
     (table `webhook_calls` : name/url/headers/payload/exception) et le principe de job
     en queue sont repris, pas le reste du package (pas de config/webhook-client.php
     publiee, pas de SignatureValidator custom)
   - StripeWebhookController inchange sur la verification de signature (memes 400) ;
     persiste un WebhookCall puis dispatch `App\Jobs\ProcessStripeWebhookJob` pour les
     events de paiement reussi seulement
   - ProcessStripeWebhookJob (ShouldQueue, tries=5, backoff exponentiel) : dedup par
     `payload->id` (event.id Stripe, deja present dans le payload brut) en ne sautant
     que sur un event deja traite AVEC SUCCES (exception IS NULL sur webhook_calls) -
     une premiere tentative echouee reste retentable a la redelivraison Stripe suivante.
     Exception ecrite sur `webhook_calls.exception` (colonne cast array : code/message/
     trace) avant d'etre relancee, pour que le retry Laravel/Horizon s'active
   - QUEUE_CONNECTION=redis en prod -> vrai retry ; =sync en test -> le job tourne
     dans la meme requete, tests HTTP existants inchanges sauf un (Bus::fake() global
     remplace par un fake selectif pour ne pas intercepter aussi ProcessStripeWebhookJob).
     2 tests ajoutes (dedup par event.id, exception enregistree + relancee)
   - Limite connue, non traitee ici (pas demande) : pas de purge programmee de
     webhook_calls (le modele est MassPrunable mais lit `config('webhook-client.
     delete_after_days')`, absent puisqu'on n'a pas publie ce config) -> la table
     grandira sans limite tant que personne n'ajoute une purge
   - Verifie : migration testee en reel sur Postgres local (`php artisan migrate`),
     requete de dedup JSON (`payload->id`) validee via tinker, `pint --test` +
     `phpstan analyse` clean sur les fichiers touches. Pest non execute (pdo_sqlite
     absent sous cette machine WSL, limite connue) -> tests ecrits mais pas
     executes localement, a verifier en CI

=== BLOQUES / PAS ENCORE PERTINENTS ===

5. [VERIFIE 2026-08-06] Watchtower (devifyo/watchtower)
   - Dashboard unifie schedules + queues + erreurs, alertes Slack/webhook/email integrees gratuitement
   - Comble un vrai trou : aucune des 7 taches planifiees (routes/console.php) n'a de
     surveillance dediee (backup:run, cart:send-abandoned-reminders, etc.)
   - BLOQUE : le dernier tag publie sur Packagist est v1.0.2 (18 juin 2026), dont le
     composer.json exige illuminate/*: ^11.0|^12.0 -> `composer require` echouerait sur ce
     projet (Laravel ^13.17), resolution de dependances impossible
   - Le support Laravel 13 existe uniquement sur la branche main non taguee (commit de2ac54,
     1er juillet 2026, "support laravel 13 and test on php 8.4 and 8.5") -> aucune release
     stable ne l'inclut, et le repo n'a meme aucune "Release" GitHub formelle (juste des tags)
   - Installer maintenant impliquerait de pointer composer sur dev-main (non semver, pas
     versionne) -> pas acceptable pour un site en prod live
   - A reverifier : attendre un tag > v1.0.2 dont le composer.json declare illuminate ^13.0
   - Chevauche Horizon (queues) et Sentry (erreurs) -> si un jour installe, seulement pour la
     partie "schedules", pas pour remplacer Horizon/Sentry
